§0 A field guide for one very confusing app badge

Why does Element keep telling you something isn't verified?

Matrix's end-to-end encryption is genuinely well designed — which is exactly why the UI can't just "turn it off" for you. This guide walks through what's actually being checked, in plain language, with real diagrams, so the next warning banner tells you something instead of just nagging you.

Reads in ~18 min, skimmable Level zero assumed knowledge Grounded in Synapse & Element Web source, not vibes

This is the entire idea. Everything below is detail on top of this one comparison.

§1 First, the cast of characters

Four names people mix up constantly

"Matrix," "Element," and "Synapse" get used interchangeably, but they're three different layers — plus your devices, which hold the one thing none of the others ever see.

Matrix
The protocol (a rulebook)
An open specification for how chat messages, rooms, and encryption keys move between servers and apps. Matrix itself has no servers or apps of its own — it's the rules everyone else follows.
Synapse
A homeserver (the mail room)
The server software that stores rooms, routes messages, and relays encrypted key material between your devices. It's one implementation of "Matrix" — the one this guide's research focused on.
Element
A client (the app you open)
The app — web, desktop, or mobile — that talks to your homeserver on your behalf. It's where every "verify this session" banner actually lives; Synapse never renders UI.
Your devices
Where the actual secrets live
Every phone, laptop, and browser tab you've logged in on generates its own private keys, on-device. This guide is mostly about how those devices learn to trust each other.

One sentence to hold onto for the rest of this page: Synapse moves things around; only your devices can prove who they are. Everything confusing about verification comes back to that one fact.

§2 The architecture

What lives where

Three kinds of data flow through Synapse. Two are things Synapse can read (they're not secret). One is a locked box Synapse only carries — it can't see inside, no matter who's asking.

§3 Untangling the vocabulary

Six different things all called "verified"

This is the real root cause of the confusion: Element and Synapse reuse "account," "verify," and "trust" for at least six separate mechanisms. Here's each one, in plain language, with who actually checks it.

Account verification

1

Proving you own an email address or phone number, usually at sign-up or password reset. Ordinary web-account stuff — no cryptography, no devices involved.

Checked by: the server

Device / session verification

2

A cryptographic claim that this specific device's keys are attested by the same identity as your other devices. This is what "Verify this session" is actually about.

Checked by: your client, from signatures

Cross-signing

3

The signature graph underneath #2: a master key signs a self-signing key (vouches for your own devices) and a user-signing key (vouches for other people's identities).

Checked by: your client, pure math

Secret storage ("4S") / recovery

4

An encrypted lockbox on the server holding your cross-signing private keys, so a new device can recover them with a recovery key instead of needing another device online.

Server carries it, cannot read it

Key backup

5

A separate encrypted lockbox — this one for your message keys, so encrypted chat history survives you losing a device. Different key, different purpose, same "server can't read it" property.

Server carries it, cannot read it

Server-side account status

6

Moderation/lifecycle flags an admin sets — deactivated, locked, suspended. Real admin power, zero connection to cryptographic trust. Easy to conflate with #2 because both use the word "account."

Checked by: the server

§4 Walk through it yourself

Four moments, step by step

Click through each one. These are traced directly from Element Web's actual verification logic, not a simplified paraphrase.

1

  1. Create your account

    Ordinary sign-up: username, password, maybe an email. No cryptography has happened yet — this is meaning #1 and #6 from §3, not device verification.

  2. Your device generates its own keys

    Element (via matrix-js-sdk's Rust crypto engine) creates a device identity keypair, entirely on-device. The private half never leaves it.

  3. Cross-signing identity is created

    A master key, a self-signing key, and a user-signing key are generated locally — the root of trust that will later let other devices and other people recognize you.

  4. Public keys and signatures go to Synapse

    Only the public halves, plus signatures proving they belong together, are uploaded. Synapse validates the signatures are well-formed and stores them — see §2's "public & signed" compartment.

  5. Recovery key / secret storage is set up

    Your cross-signing private keys get encrypted with a recovery key you keep, then that ciphertext is stored server-side as "secret storage." Skipping this step is the single biggest cause of repeat nagging later — see §6.

  6. Result: verified, trivially

    With one device and no one else to compare against yet, you're automatically the root of trust. The real test comes with device #2 — next tab.

1

  1. Same password, new device

    Matrix accounts aren't tied to one machine — logging in on a new phone or browser is completely normal and expected.

  2. The new device is a stranger, cryptographically

    It generates its own fresh keys. Nothing about them is inherently connected to your other devices yet — they need to be vouched for.

  3. Element notices and nags you

    This is Element's DeviceListener doing its job: this device isn't cross-signed yet, so it shows "Verify this session." This is meaning #2 from §3, working as intended — not a bug.

  4. Two ways to resolve it

    Path A needs another already-verified device online: both devices compare a short row of emoji (or scan a QR code) and confirm they match. Path B needs your recovery key: it decrypts your existing cross-signing private key straight from secret storage, no other device required.

  5. Trust is established

    Path A produces a fresh cross-signature between the two devices. Path B recovers the exact same private key your other devices already trust. Either way, only a signature or a locally-decrypted key moves — never anything Synapse can read.

  6. Result: this device is now trusted

    The toast disappears. Other people who'd verified you before will now see this device as trusted too, automatically, via the signature chain.

1

  1. Emoji (or QR) comparison — "SAS" verification

    Two live devices show the same short sequence of emoji or scan a QR code. It's a human-friendly way to compare a cryptographic value without either device having to trust a server to do it.

  2. A match creates a real signature

    Once you both confirm the emoji matched, each device cryptographically signs the other's public key. That's the actual "verify" action — not a checkbox, a signature.

  3. Only the signature travels

    That signature is uploaded to Synapse as an ordinary, public, opaque blob (§2). It proves a fact happened; it reveals no secret.

  4. Recovery key does something different

    Instead of asking another device to vouch for you, a recovery key unlocks the same private cross-signing key your account has always had, straight out of secret storage. No live second device required.

  5. The dead end: reset identity

    If you've lost the recovery key and every other device is signed out, there is no way to recover the old private key — encryption doesn't have a back door. Element's "Reset cross-signing / reset encryption" flow starts over: new keys, and access to old encrypted history is gone unless it was in a working key backup.

⚠

Reset is a last resort, and it's yours alone to run

An admin cannot do this reset for you and cannot skip it on your behalf — it requires your account password and runs entirely in your own client. After a reset, people who verified you before will see "digital identity changed" until they verify you again. That warning is the system working correctly, not a glitch to suppress.

1

  1. Check 1 — is this device itself trusted?

    Element's listener asks first: does this session's own cross-signing status check out? If not, everything else is skipped and you get "Verify this device." This single check explains most of the nagging most people see.

  2. Check 2 — are the cross-signing secrets cached?

    Even a cross-signed device needs its private cross-signing keys loaded in memory/local storage. If they're missing but recoverable, you get a sync-mismatch warning; if they're missing everywhere, Element concludes your identity needs a reset.

  3. Check 3 — is key backup uploading?

    If you haven't explicitly turned backup off, Element expects it to be actively saving your message keys. A stalled upload produces its own distinct nudge.

  4. Check 4 — is recovery (secret storage) ready?

    This is the "have you actually finished setup" check — the one most easily fixed once, permanently, by completing recovery setup properly the first time (§6).

  5. Check 5 — can backup be read back?

    Last check: can the client actually decrypt the backed-up message keys? A "yes" up to here but a "no" now still shows a sync warning.

  6. Only one alert shows at a time

    This is a waterfall: the first failing check wins and its toast is shown; later checks aren't even reached. That's why the message you see can change from visit to visit — you're not seeing five bugs, you're seeing one check at a time.

§5 The question everyone eventually asks

Can you just... edit the database to make it say "verified"?

Short answer: not the way you'd hope. Here's the precise version, because "no" alone isn't satisfying and isn't quite complete either.

synapse/storage/schema — e2e_cross_signing_keys (simplified)
user_idkeytypekeydatastream_idverified
@alice:example.org master {"keys":{"ed25519:…":"…"},"signatures":{…}} 4821 — column does not exist —
@alice:example.org self_signing {"keys":{…},"signatures":{…}} 4822 — column does not exist —

This is the real, current schema — not a paraphrase. keydata is public key material plus a signature, both opaque blobs. There is no boolean anywhere in Synapse's schema that means "verified." An admin can't flip a switch that doesn't exist.

What's confirmed vs. what's uncertain

Confirmed by reading the source: the schema has no verified flag; upload endpoints cryptographically check signatures before storing them (bad signatures are rejected with M_INVALID_SIGNATURE); the one admin-adjacent cross-signing endpoint (_allow_cross_signing_replacement_without_uia, Synapse 1.97.0+) only waives a re-auth prompt for a user's own client to upload a brand-new, self-consistent key — it cannot implant trust in an existing device. A real historical bug (synapse#16398) let duplicate key rows pile up, but that's disk bloat, not a trust bypass.

Genuinely uncertain: this is based on a source-level review of the current codebase and public issue history, not an exhaustive audit of every closed security advisory ever filed. I found no working exploit of this kind — but "I didn't find one" and "one has never existed" aren't the same claim.

⚠

This one is real — and it only fools you

matrix-js-sdk does have a local "trust this device" call — but it writes to your own browser's encrypted local store (IndexedDB), not to the server. There is no network request involved. It changes what your own client shows you. It changes nothing about what anyone else's client computes, because they never see your local database.

This is why a screenshot of a green checkmark proves nothing to anyone but the person who took it. It's a real local override, with a real (if narrow) security consequence: it can lull that one user into trusting a device they never actually verified — but it cannot forge trust in anyone else's eyes.

§6 For whoever runs the homeserver

What an admin can and can't do

If you're self-hosting Synapse, here's the honest capability boundary, followed by what's actually worth doing about the UX.

✓ Can do

  • List, rename, and delete devices via the admin API.
  • Deactivate, lock, or suspend accounts (meaning #6 from §3).
  • Force the verification workflow client-side with force_verification (below) — friction, not forgery.
  • Destroy a user's cross-signing/secret-storage state, forcing them to redo setup from scratch.
  • Grant a 10-minute UIA-free window for a user's own client to upload a new master key — only relevant if you delegate auth to Matrix Authentication Service.

✕ Cannot do

  • Mark a device or user as cryptographically verified — no such field exists to set.
  • Grant trust on someone's behalf — it requires the private key material only their own devices (or their recovery key) hold.
  • Read secret storage or key backup contents — both are encrypted before they ever reach the server.
  • Bulk-verify an entire user base in one action, by design.
  • Undo a user's identity reset for them, or skip it on their behalf.

Remediation

What's actually worth doing

1

Align client versions first

Mixing very old (pre-Rust-crypto) clients with current ones is a documented source of stale, contradictory verification state. Keep mobile, desktop, and web current across your users.

2

Make recovery setup mandatory at first login

A properly stored recovery key is what lets a brand-new session self-verify against secret storage instead of needing another device online. Skipping it is the actual root cause of most repeat nagging (§4, flow 4, check 4).

3

Turn on force_verification

Element Web's own config flag removes the "skip" button on first login, so setup completes immediately instead of leaving unresolved state to surface later as confusing toasts.

// config.json
{
  "force_verification": true
}
4

Know the one real "reset" path — and its cost

For a genuinely unrecoverable identity (lost recovery key, no other session), the only supported fix is the user's own client-side "Reset cross-signing / reset encryption" flow. It requires their password, cannot be run by an admin, and permanently loses access to any encrypted history that wasn't in a working key backup.

5

If a future audit script would help, keep it read-only

The only defensible scope: enumerate (via the admin API) which accounts have never set up cross-signing at all, purely to target outreach ahead of the deadline below. Never a script that writes to any trust-related table — there is nothing there to write that would do anything.

§7 Why this is worth fixing soon

Element is about to start enforcing this

—days until enforcement

Unverified sessions will stop sending and receiving encrypted messages

Element Web already ships this exact string in its verification prompt: "As of end of October 2026, unverified devices will not be able to send and receive messages." Per Element's own announcement (originally slated for April 2026, pushed to October 2026), this is enforced client-side — not a Synapse setting you can toggle off. After the deadline, unverified sessions go effectively silent in encrypted rooms.

Element's announcement →

For a self-hosted deployment, this is the actual deadline driving urgency — independent of anything a database could fix. It's worth running a "get everyone verified and recovery-key-configured" push well ahead of it, using §6's remediation list.

Reference

Glossary

Matrix
The open protocol/rulebook for decentralized chat and E2EE — not a company, app, or server by itself.
Synapse
The most common homeserver implementation of Matrix — the server software.
Element
A Matrix client app (web/desktop/mobile) built on matrix-js-sdk.
Device / session
One logged-in instance of a client — a phone, a browser tab, a desktop app each count separately.
Cross-signing
A signature graph (master, self-signing, user-signing keys) letting your devices and other people vouch for identities without a server in the loop.
Secret storage ("4S")
Server-hosted, client-encrypted storage for your cross-signing private keys and backup key.
Recovery key
The secret (key or passphrase) that decrypts secret storage. Never sent to the server in plaintext.
Key backup
Server-hosted, client-encrypted storage for your message (Megolm) decryption keys, so history survives a lost device.
SAS verification
"Short Authentication String" — the emoji/number comparison used for live, in-person device verification.
UIA
User-Interactive Auth — Matrix's term for re-confirming your password before a sensitive action.
Identity reset
Discarding your cross-signing keys and starting over. Destructive, client-side only, and not reversible.
MAS
Matrix Authentication Service — an optional OIDC-based auth delegate some Synapse deployments use instead of Synapse's own password auth.
